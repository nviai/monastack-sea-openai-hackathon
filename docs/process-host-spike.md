# Process isolation experiment

This is a local isolation experiment, not a Codex runner or production security boundary. The opt-in one-shot worker described in `host-claims.md` uses it for a configured command; the app and node do not start it automatically. The experiment never mounts the live workspace, calls a model, or authenticates an agent by itself. The Codex CLI was exercised with a fake local model response; no real-model execution has been verified.

`backend/process-node/container_spike.py` launches an explicitly supplied command in an already-present Docker image specified by its image ID. The container has no external network route, a read-only root, a single caller-supplied writable bind mount, a non-root UID matching the caller, no added capabilities, `no-new-privileges`, disabled container logging, a PID limit, a memory limit, and a CPU limit. The worker requires an explicitly local Unix Docker socket and refuses Docker host/context environment overrides; an operator must still verify that the socket is not forwarded to a remote daemon. An opt-in flag adds a size-limited ephemeral `/.codex` for the synthetic Codex image; `/tmp` is also ephemeral. The caller must use a disposable private directory, never the live workspace. A separate watchdog attempts to remove the container if its parent dies or a local deadline expires. Input and output are bounded; a timeout or cancellation removes the randomly named container created by that invocation. The routine uses no shell unless the explicitly supplied command itself is a shell. It does not automatically pull an image.

On the development Mac, `python3 backend/process-node/probe_container.py` ran synthetic commands in the already-present Alpine 3.23 image, checking that the mounted directory was writable, a synthetic sibling file was not mounted, root writes failed, the container had no routes, timeout and cancellation returned, output was capped, and its test containers were removed. These tests are limited: they do not prove protection against kernel or Docker vulnerabilities, denial of service outside the configured limits, all host metadata leaks, or races during daemon failure. Docker control itself is privileged. The test exposes only synthetic data to the container and does not establish safety for user workspaces or secrets.

An initial macOS `sandbox-exec` experiment with a strict file-read allowlist failed to launch the test shell on this machine. Broadening the policy to all file reads made the shell start, but would not meet the desired data isolation, so that policy was not adopted. The experiment is used by a limited worker with scoped credentials and claims, but it is not a substitute for a configured Codex/provider setup, enforced model budgets, workspace access controls, and adversarial production testing. Real execution must remain explicitly configured and disabled by default. The user's prompt prohibits sending workspace data outside the workspace without explicit authorization.

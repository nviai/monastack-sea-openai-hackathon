# Later-stage prototype slices

Update: direct conversational OpenAI agents are now implemented separately from the proposal/host execution pipeline described below. See [OpenAI office chat](openai-agents.md). Real provider execution still requires a configured API key; the Codex worker remains a synthetic experiment.


None of Stages 3–6 is complete. These slices run inside the existing loopback office-node prototype and inherit the limits in `stage-1-status.md`: no production identity, TLS, encrypted storage, device enrollment, general access-management UI, a general-purpose client outbox, or remote deployment. The limited task outbox is described in `stage-2-status.md`. All records below are stored as server-readable SQLite data. They are not suitable for confidential or production use.

## Stage 3: agent proposals

A connected human can create an immutable instruction proposal for a seeded agent, optionally linked to a task from the board or through the API. An unlinked proposal is visible to every authenticated workspace member. A proposal linked to a task follows its project access and is omitted or denied after access is revoked; do not put secrets in proposals. A seeded organization administrator can approve; its creator or an administrator can cancel. Decisions, versions, and audit events are stored transactionally with idempotent operation IDs. The UI shows the history. A macOS app-to-node integration test created and approved a proposal, and a second HTTP identity saw the waiting state. Approval moves the proposal to **approved, waiting for host**. A local operator can explicitly enroll a host credential scoped to one human sponsor and one agent. Claims are disabled by default. When enabled, an approved job may be claimed by one host for at most 30 seconds, with a unique fence. The node rechecks the sponsor’s current project edit access on claim and report. A host can poll whether its claim remains active and submit a fenced report; lost claim responses can be retried by the same host, while expired claims are never automatically reassigned. Disabling host claims invalidates outstanding claims even after re-enabling. An explicitly configured one-shot worker can consume a claim and run a fixed command in an isolated, networkless Docker container with an empty temporary directory. Synthetic integration tests cover a report, cancellation of a running container, the global stop control, a worker crash and node outage. The worker does not mount the workspace, produce a PR, or run Codex by default. A host report is not independently verified. There is no configured Codex runner, MCP or verified real agent execution. The displayed budget is merely a requested number of units; it is not enforced and has no defined cost model. Agent profiles remain offline. A proposal or approval is not evidence of completed work. The worker and isolation limitations are described in `host-claims.md` and `process-host-spike.md`; the Codex CLI has been exercised through the worker only with a fixed synthetic localhost response, not a real model or workspace; see `codex-evaluation.md`.

## Stage 4: documents

Connected users can create, edit, and search server-readable text documents in the workspace or a room scope. Each request checks current room membership; a restricted document is omitted from search and returned as not found after access is revoked. Updates use expected versions and audit records, not generic last-write-wins. The HTTP smoke test covers restricted search/read denial, updates, duplicate retries, stale versions, and revocation. A macOS app-to-node test created a workspace document and a second HTTP identity read it; the app view also has widget coverage. Documents have no attachment support, deletion, collaborative merge, indexed search, offline cache or restore UI. Document history shows scoped audit metadata; the node rechecks room access on each history request.

The meetings view schedules, reschedules and cancels simple records in a workspace or room scope. Times are entered and displayed explicitly as UTC; valid ranges are bounded to 2000–2100 and at most seven days. A meeting is visible only while the viewer has scope access, and its creator can reschedule or cancel it while authorized. Cancellation uses version checks, idempotent retries and audit history. The HTTP smoke test covers private-room denial, duplicate retry, stale cancellation and access revocation. This is a simple list, not a full calendar: it has no recurring events, time-zone conversion, invitation, attendance, reminders, video or voice. A basic scoped whiteboard stores text notes with normalized positions. People with current workspace or room access can add, edit, move and delete notes; deletion leaves a tombstone and audit events. Version checks reject concurrent stale changes, retries are idempotent, and the board refreshes while open. It has no rich drawing, attachments, offline merge, note restore UI or real-time streaming. Cloud inference is not implemented. An optional, explicitly started loopback MLX service lets the app generate text from a user-entered prompt; it does not automatically access workspace records and is not Mona or an agent runtime. The pinned model, measurement and setup are documented in `local-model-spike.md`. The local service and macOS screen were tested using synthetic text.

## Stage 5: customer records

The local customer directory can create and edit a name, optional email and notes. It does not send messages, contact addresses, import the earlier CRM dataset, or connect to external services. The trusted node permits seeded Sales, Support and organization-admin roles and denies other roles by default; role grants are an explicit demo assumption from the seed, not a statement of current employment. Changes use expected versions and transactional audit records. Tests cover denied users, allowed users, stale changes, duplicate operations and role revocation across restart. A macOS app-to-node test created a customer record as an administrator; the UI also has a denial widget test.

A local sales pipeline links opportunities to those customer records. Sales and organization-admin roles can create and advance an opportunity through lead, qualified, proposal and won, or mark a nonterminal opportunity lost; support can read but cannot modify opportunities. Transitions are version checked and audited, retries are deduplicated, and current roles are checked before replay. The UI offers history and confirmation. This pipeline does not send messages, create contracts, record amounts, or perform financial transactions. There is no external integration, search, deletion, record-level sharing or retention policy. Data is readable by the node and all authorized customer roles.

The contract-proposal view records immutable title and proposed text linked to a customer. Only Sales and organization administrators can read and propose; a different organization administrator can approve internally or reject, while the creator can withdraw a pending proposal. The confirmation displays the frozen terms. Current roles are checked again for retries, and transitions use version checks, transactional audit and idempotent operation IDs. The list refreshes while open and clears on access failure. A macOS integration test creates a synthetic proposal; HTTP tests cover role denial, self-approval denial, concurrent decisions, revocation, retries and backup restoration. This is an internal review record only: it does not create a signed or binding agreement, provide legal review, send anything to a customer, support amendments or attachments, or integrate with external signature systems. The node stores the terms as plaintext.

The customer directory, sales pipeline and support-case lists refresh while open. They clear records on access failure and update write controls when role capabilities change; widget tests cover both full access loss and retained read-only access. Already opened record editors or histories can retain previously viewed information until closed.

Customer bookings are local UTC records linked to customers. Sales and administrators can create, reschedule and cancel; Sales, Support and administrators can read. The node rejects overlapping scheduled intervals for the same customer within the local database, permits adjacent intervals, checks versions and current roles, and records idempotent operations and audit events. A two-node contention test checks overlapping requests, and a macOS app-to-node test creates a synthetic booking. This does not check staff or room availability, place a reservation externally, send invitations, synchronize calendars or notify customers. There is no recurrence, reminder, timezone conversion or pagination; the list is limited to 200 records sorted by start time. Records are server-readable.

The customer-support view also records simple cases linked to a customer. Support and organization-admin roles can create and move a case through open, in progress and resolved, and reopen a resolved case; Sales can read but cannot change cases. Transitions are version checked, audited and idempotent. This local workflow does not send messages, track a service-level agreement, accept attachments, import messages or connect to external ticket systems. Customer roles can read all cases, and the node can read their contents.

## Stage 6: expenses, leave requests and incidents

The local expense view records a description, positive integer amount in minor units, a three-uppercase-letter currency code, creator, state and history. The code only checks the *shape* of the currency string; it does not validate ISO codes, exchange rates, or currency-specific minor units. Finance/accountant and organization-admin roles can view and propose; only an organization admin other than the creator can approve or reject, and the creator can withdraw a pending proposal. The UI requests confirmation and states that no payment occurs. State changes use versions, idempotent operation IDs and transactional audit records. HTTP tests cover denied roles, no self-approval, concurrent/stale decisions, retries and role revocation. A macOS app-to-node test created an expense and a second authorized HTTP identity read it; decision confirmation has widget coverage.

The local journal view records a single-currency two-line entry with equal positive debit and credit amounts, distinct local account codes and an immutable posted state. A finance user can propose or withdraw a pending entry; an organization admin other than the creator can post or reject it. Decisions use version checks, idempotency and audit, and current authority is checked on retries. A posted original can be corrected by proposing a separate reversal with the debit and credit exchanged; a different administrator must post it, and at most one reversal can be posted for each original. A net-activity view sums posted entries by account and currency using wide integer arithmetic and does not include opening balances. A separate posted-activity balance groups account net debits and credits by currency and displays per-currency totals as integer minor-unit strings. It excludes unposted entries, incorporates posted reversals, and does not combine currencies. HTTP and widget tests cover authorization, unposted entries, reversals, multiple currencies and display; an isolated macOS app-to-node test displays a synthetic posted balance. This is not a financial statement or a complete trial balance with opening balances. This is a minimal local journal, not a complete accounting system: account codes are not validated against a chart of accounts, currency codes are shape-checked only, and there are no fiscal periods, tax or full reports. Posting does not initiate a payment. The records are plaintext on the node.

An internal payment-authorization view can request approval for an already approved expense. The amount and currency come from that expense; only one pending or approved authorization per expense is allowed. An organization administrator who is neither the requester nor the expense creator can approve or reject, and the requester can withdraw while pending. Decisions are version checked, idempotent and audited. An eligible organization administrator can revoke an approved authorization; a new authorization can then be requested for that expense. A synthetic macOS app-to-node test verifies revocation and its stored version. Revocation changes only the local approval record and cannot reverse an external payment. Approved means **waiting, no payment executed**: no beneficiary, bank connector, transfer or payment reconciliation exists. This record cannot be used as proof that money moved.

A separate leave-request slice allows each authenticated human to submit and see their own request and history, and withdraw a pending request. Withdrawals are version checked and audited. For approved leave, the requester can propose cancellation or withdraw a pending cancellation; a different HR-authorized person must approve or reject it. Rejecting the cancellation returns the leave to approved. All steps require current versions and are audited; retries recheck current authority. HTTP tests cover concurrent decisions and self-approval denial. A macOS integration test creates an approved synthetic request, requests cancellation in the app and confirms a different test HR identity can approve it. A person with an explicitly granted `hr` role can view and decide other people’s requests, but cannot decide their own. The leave list refreshes while open; a widget test checks that other people’s requests disappear after role access is removed. Organization-admin status alone grants no HR access, and the seed grants no HR role. The HTTP test temporarily grants an HR role in an isolated database to verify this boundary; it does not add an HR employee to the seed. A macOS app-to-node test submitted a leave request and verified that a second non-HR identity could not see it. Dates are validated as real calendar dates and ranges of at most 366 inclusive days. A monthly approved-leave calendar shows the requester and date range, including approved requests with cancellation pending; it does not include the reason. Each node request restricts results to the current person or explicitly authorized HR and rechecks that authority. The view refreshes every five seconds, clears data on errors, and ignores late responses from an earlier month. It uses calendar days for 2000–2100 and warns when the first 500 records do not cover the complete month; it has no pagination. HTTP tests cover role revocation, cross-month leave and cancellation. An isolated macOS app-to-node test displays synthetic approved leave, verifies the 500-record boundary and rechecks HR revocation. Authentication, HR role and calendar records are read from one SQLite snapshot; an already-authorized in-flight response cannot be recalled. The calendar is not a leave balance, payroll record, attendance proof, holiday or workday calculation. There is no HR role-management UI, leave balance, accrual, cancellation reason, attachment or payroll integration. The node and its database can read the private data.

Incident reports can be filed by authenticated humans and viewed by their reporter and explicitly granted `operations` responders. The reporter cannot transition their own report, even if they are a responder. A different responder can move an incident from open to investigating to resolved. Each transition requires a current version and produces an audit event; retries use an operation ID. The seed grants no operations role and there is no role-management UI. An HTTP test grants and revokes this role only in an isolated test database. A macOS app-to-node test created a synthetic incident and verified another non-responder could not see it. The reporter and current operations responders can post immutable text updates in a scoped discussion. The node checks current access before each read, write and retry; comment writes and audit events commit together, and unchanged retries reuse an operation ID. The incident list and discussion refresh while open; inaccessible incidents disappear from the list and displayed discussion updates are cleared when a refresh fails. The API returns the latest 500 updates without pagination; editing, deletion, attachments and offline delivery are not supported. HTTP tests cover denied users, role revocation, duplicate retries and content bounds; a widget test covers lost-response retry and clearing after access removal, and the macOS integration test posts a synthetic update through the app. This is a basic record workflow, not alerting, escalation, on-call scheduling or a production incident-response system. Records are plaintext on the node.

For local prototypes, a person with operating-system access to the node database can explicitly grant or revoke `hr` or `operations` for an existing human using `MONASTACK_DB=/path/to/office.sqlite3 backend/office-node/target/debug/monastack-office-node role grant operations ACTOR` or the corresponding `role revoke` command. These commands do not create an actor or a missing database. Each change is transactional and recorded as a `local-operator` event in `security_audit`; duplicate grants and revocations fail. This is a trusted local operator mechanism, not authenticated remote role administration. Backups can restore old grants, so verify and reapply later revocations after a restore.

Expense, journal and payment-authorization writes authenticate and check current roles within immediate SQLite write transactions. A synthetic two-node test sharing one local database covers concurrent reversal posting, duplicate payment requests, HR and incident decisions, document, meeting, whiteboard, task and sales conflicts, chat races and duplicate presence heartbeats on one realtime service, plus permission or credential revocation while writes wait for the database lock; run `python3 backend/office-node/tests/multi_node_finance.py` after building the node. This does not establish distributed deployment or financial-system correctness.

Expense, journal and payment-authorization lists, and the two journal activity reports, refresh while open and clear their records after an access or node error; widget tests cover revocation. The expense and journal views also poll current approval capability and hide approval or posting controls when it is absent; the node independently checks authority on every decision. This does not remove data already read. Expense, journal and payment forms, confirmation and history dialogs hide their earlier contents after a refresh detects lost access, a node error, or loss of approval authority; late history responses are ignored and old dialogs do not restore their contents if access returns. Journal reversal confirmations have the same protection. Access changes may remain visible until the next poll, and the server independently checks each write.

These records do not form a complete accounting system and do not perform payments, reimbursements, tax calculations or financial reporting. There is no evidence upload, cancellation of approved expenses, policy management, approval delegation, monetary conversion, retention or compliance review. The node supports a local snapshot and restore procedure, described in `stage-1-status.md`; this is not an encrypted or managed backup service. Broader HR records and workflows, expenses beyond this basic approval, complete accounting, payments, and broader operations workflows are not implemented. The empty HR room does not grant HR authority and no HR personnel have been invented.

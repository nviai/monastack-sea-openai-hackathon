# Experimental host claims

The node API records ownership and reports; it does not itself run code, connect to Codex or prove that an agent performed work. It is disabled by default. Host credentials are separate from human credentials and are scoped to one existing human sponsor and one agent. A locally trusted operator can enroll one by feeding a unique random token on stdin:

```sh
umask 077
openssl rand -hex 32 > local-host-token.txt
MONASTACK_DB=/path/to/existing.sqlite3 backend/office-node/target/debug/monastack-office-node host-enroll HOST_ID HUMAN_ID AGENT_ID < local-host-token.txt
MONASTACK_DB=/path/to/existing.sqlite3 backend/office-node/target/debug/monastack-office-node host-claims enable
```

`HOST_ID` is a unique 16–80 character ASCII identifier. The node stores a hash of the token. A host can read `GET /v1/host/jobs` and request `POST /v1/host/claim` with `{"job":"..."}` using its own bearer token. Only approved jobs for its configured agent are available; task-linked jobs require its sponsor's current project editor access. A claim has one owner, an opaque fence and a fixed 30-second wall-clock deadline. A repeated claim by the same host returns the same fence while active; a competing host cannot take it. Expired or interrupted claims are never automatically requeued. A host can query `GET /v1/host/jobs/{id}/control` and post a bounded report to `/v1/host/jobs/{id}/report` with the fence, outcome, summary and stable operation ID. The UI labels reports as unverified and displays them only to people who can access the linked task. Report contents are plaintext on the node.

`host-claims disable` stops new claims and permanently expires existing claims even if claims are enabled again. `host-revoke HOST_ID` invalidates that host's credential. Both operations require local operating-system access to the database and are recorded as local-operator actions. The optional one-shot worker polls control and attempts to remove its own container when a claim becomes inactive, its credential is revoked, the node is unreachable, or its monotonic deadline passes. A separate watchdog attempts removal if the worker dies. Synthetic tests cover running cancellation, the global stop control, worker termination and node outage. A separate macOS integration test confirms that a real worker report appears in the app as unverified. The node cannot force arbitrary external processes to stop; a Docker daemon failure, host crash or malicious host can defeat cleanup. Cancellation is a control record, not proof of termination.

The existing budget remains an unenforced requested unit count, not a time, token or money limit. The node claim deadline is 30 seconds; the prototype worker independently caps wall time at 25 seconds. Neither enforces model token or monetary budgets. Clocks, bearer credentials, SQLite data, restore of old snapshots, and separately hosted workers are not hardened. Do not use this prototype to execute sensitive or external actions. A real host requires isolated workspace access, scoped credentials, an explicitly configured local or authorized provider, content-bound approvals, enforced budgets, durable output and adversarial tests before it can be called operational.

## One-shot synthetic worker

The worker is never started automatically. It accepts a literal loopback node URL, a private host token file, an already-present image ID, and an explicitly supplied JSON command array. It passes the approved instruction to that command on stdin, mounts only a fresh private temporary directory, disables external container networking, and reports a bounded output to the node. The temporary directory is removed after normal execution; an abrupt host failure may leave it behind. It does not mount the workspace, produce a patch or PR, or configure Codex or a model provider. The CLI has been tested through this worker with a synthetic local provider; no real-model or workspace run has been verified. See `codex-evaluation.md`.

For a synthetic test only, `python3 backend/process-node/test_worker.py` creates an isolated node, credentials, jobs and disposable containers; it does not use the user's workspace records. An explicitly configured operator can invoke `backend/process-node/worker.py --help` for the one-shot interface. Do not use real instructions or sensitive data with this prototype. The worker requires a Unix Docker socket, refuses Docker host/context environment overrides and disables container logging. The operator must verify that the socket is local and not forwarded; the Docker daemon and container image are trusted dependencies. Its isolation has not received an independent security review.

# Stage 2 task prototype

Stage 2 is not complete. The office node now has versioned HTTP endpoints for projects, tasks, assignment changes, task transitions, comments, and task history. A connected human can open the task board, create and select a project, create tasks assigned to seeded people or agent profiles, move tasks through To do, In progress and Done, add comments, and inspect history. Agent assignment is a record only; no runtime is started. Changes, deduplication records and audit events are committed together in SQLite. A retried operation ID with the same actor and request is accepted once; a different request using that ID is rejected. Updates use a version check and return conflict for stale writes. Write authorization and version checks run in the same immediate SQLite transaction; a synthetic two-node test covers competing task transitions and project membership revocation while a write waits. The Rust core defines permitted state transitions.

This is a loopback prototype with a limited durable task-command outbox; chat uses a separate local queue described in `stage-1-status.md`. A new project can be workspace-visible or private. Existing projects retain workspace visibility. Private projects are visible to their owner and explicitly invited human members; only the owner can grant or revoke membership, and organization admins have no automatic override. Membership changes are audited and project history is visible to current members. The board refreshes access approximately every five seconds and clears inaccessible task views on refresh or connection failure; already-read plaintext cannot be revoked from a device. Private project owners can grant read-only or editor access, and can change or revoke a member’s role; previously invited members remain editors. Read-only members can inspect tasks, comments, history and linked proposals but cannot change them or create linked proposals. Workspace-visible projects remain editable by all authenticated members. There are no device identities or production security claims. Task project creation, task creation, transitions, assignment changes and comments are written to a Rust/SQLite outbox before delivery; their operation IDs survive restart. On reconnect the node rechecks authorization and versions. Rejected changes remain visible for review and explicit discard and pause all later queued changes to preserve order; a lost response can be replayed without duplicating an operation. The queue is scoped to actor and persistent node identity (a local database identifier, not a cryptographic server identity), holds at most 1,000 pending/rejected entries per scope, and stores command contents unencrypted in the macOS app container. It retains delivered and discarded history; no retention or secure erasure exists. Project-membership changes and other features are not queued. This is not a full offline editing or snapshot system: no offline permission lease or cached private project data is offered. Discard cannot undo a command already received by the node. History records actor, action and time; there is no tamper-evident audit, retention policy, export or admin UI. A task can open the proposal UI with its task link; the resulting job inherits project access but does not run. Tasks are not yet connected to documents, Mona or other later-stage records.

Automated coverage includes task-domain transition tests, app widget tests with a fake request adapter, and a real node HTTP smoke test covering creation, agent assignment, reassignment, comments, audited transitions, idempotency, concurrent version conflict, restart, private-project denial and membership revocation, and backup contents. A native-bridge test checks queued operations across storage reopen and conflict rejection. A macOS app-to-node integration test simulates a committed command with lost responses, reopens the local queue, and verifies that replay does not duplicate the project; it also checks a rejected conflict. A macOS app-to-node integration test also created a project and task in the board, transitioned it, inspected history, and verified the assignment and state through a second HTTP identity. The runner reported that it could not foreground the app; task-board interaction between two actual apps remains unverified. A separate two-app office presence and chat test is described in `stage-1-status.md`. Run `cargo test --manifest-path core/Cargo.toml`, `cargo build --manifest-path core/Cargo.toml`, `cargo test --manifest-path backend/office-node/Cargo.toml`, `cargo build --manifest-path backend/office-node/Cargo.toml`, `python3 backend/office-node/tests/http_smoke.py`, and from `app` run `MONASTACK_CORE="$(cd ../core && pwd)/target/debug/libmonastack_core.dylib" flutter test` and `flutter analyze`.

Before completing Stage 2, add finer-grained project permissions and delegation, full offline editing, dependency-aware reconciliation, richer conflict resolution, comprehensive future schema migrations and recovery, two-client task-board app tests, and production hardening. Stages 3–6 contain only the limited slices described in `stages-3-6-status.md`; they are not complete. Full agent execution, CRM, sensitive HR and financial workflows must not be inferred from the task board.

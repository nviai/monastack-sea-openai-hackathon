The moment

Agents can now rebuild almost any app.
So why are we rebuilding apps made for humans?

github.com/morluto/rea

~408k ★

"Reverse Engineer Anything": one MCP server for reverse engineering binaries, apps and runtime behavior. Agents can take apart well-known software and rebuild similar features.

It's one of the most talked-about repos in AI right now, and it deserves the attention.

Our take: it's a great party trick

  • A recreated app still has a human interface: menus, tabs, dashboards, settings pages.
  • The next big user of software is an agent acting on our behalf, not a person clicking.
  • Cloning yesterday's UI gives the agent the same mess it already struggles with.

Why clone the past when the user itself is changing?

Acknowledge REA respectfully. It's impressive and popular. Our point: reverse-engineering and re-implementing human-centric apps is fun, but it optimizes for the wrong user. Bridge to the next slide: agents see differently.

The trend

Teams are pulling everything into one project (monorepos, single workspaces) so it's easier to manage and so AI can read it all.

The catch

Pouring every silo into one place moves the mess without cleaning it. Twelve data models, duplicate customers and conflicting records end up in the same context window.

Every department picks its own SaaS. Many companies now start "one project" setups (monorepo + shared workspace) for manageability and AI readability. But consolidation without a shared schema just centralizes the noise.
Problem 2 · Context quality

Messy context makes agents confidently wrong

01

Noise

Logs, signatures and UI clutter bury the facts that matter.

02

Context poisoning

One wrong fact or earlier hallucination gets reused as truth.

03

Overload

Too much context, so the model fixates on history and misses the task.

04

Confusion

Irrelevant tools and documents push it toward the wrong action.

05

Clash

CRM says "active", billing says "churned". Which one is right?

06

Staleness

Old records with no version or timestamp look current.

07

Duplicates

"ABC Co.", "Cty ABC", "abc corp": is that three customers or one?

08

Leakage

The agent reads data its requester was never allowed to see.

09

Prompt injection

Instructions hidden inside tickets, emails and documents.

10

Context rot

Recall drops in long contexts (the "lost in the middle" effect).

Garbage in → confident garbage out

The result is hallucinations, bad decisions and unsafe actions, and a bigger model doesn't fix bad inputs.

Walk through 3–4 of these quickly, not all ten: poisoning, clash, duplicates, injection. The point: hallucination is often a data problem, not only a model problem. Feeding agents raw SaaS exports makes this worse.
Our answer

Monastack: rebuild the foundation for agents, not the apps

One AI-native stack, designed in from day one: simpler, cleaner, and easy for both agents and people to work with.

PILLAR 1

Clean by construction

Every source writes through standard schemas at the gate. Data is typed, deduplicated, versioned and permission-scoped before any agent reads it.

PILLAR 2

Agents as coworkers

Agents have identities, desks, voices and an auditable work history. You talk to them like colleagues in a virtual office instead of shuffling cards on a board.

PILLAR 3

Edge-first mesh

Local AI on every site, peer data nodes with replicas, and frontier LLM nodes used only when a task needs them. The result is lower server cost, privacy and offline resilience.

…all built on proven open source wrapped with MCP, instead of rewritten from scratch.

Three pillars. Emphasize: we don't re-implement Zendesk or Odoo. We build the AI-native layer (schemas, identities, policies, agents) and plug in battle-tested open source underneath.

Pillar 1 · Clean by construction

Standard schemas clean data at the gate, before it reaches any agent

// one envelope for every record { "id": "case_01JBX4…", "type": "support.case.v1", "tenant": "nviai", "scope": { "room": "customer-support" }, "actor": "agent:cskh-agent", "version": 7, "op_id": "op_9f2…", "source": { "system": "chatwoot", "ref": "conv/4821" }, "links": { "customer": "cus_…", "order": "ord_…" }, "untrusted": ["body"] }

Fixes noise → typed fields · poisoning → provenance · clash → one owner per field · staleness → versions · duplicates → stable IDs · leakage → ACL at retrieval · injection → quarantined text

This is the heart of the product. Customer support, warehouse, dev, app, HRM, CRM and finance all write through the same gate. Agents never read raw exports; they get small, fresh, permission-filtered context packs with citations back to records. Map each failure mode from slide 5 to a fix.
Pillar 2 · Agents as coworkers

Talk to agents like colleagues, not tickets

  • A 2.5D virtual office: Lobby with Mona's desk, Dev & QA, Product, Sales, Support, HR, Finance, Meeting, Lounge.
  • Every agent has an identity, role, desk and presence. Presence comes from a real runtime heartbeat, so offline means offline.
  • Walk up and talk: chat, DM, voice, or pull an agent into a meeting, the same way you would with a human.
  • Room policy = data policy. What an agent can hear, read and do depends on the rooms it's allowed into.
  • Every action leaves an auditable work history.
This is the "AGI-style" interaction: operators don't fill forms or drag cards; they direct agents the way they'd direct people. Seeded agents: Mona (assistant / chief of staff), dev-agent, qa-agent, pm-agent, sales-agent, cskh-agent. Agents are separate principals from humans. Restricted rooms (HR, Finance) default-deny, and the server enforces this, not just the UI.

  • Budgets and deadlines
  • Durable, fenced job ownership
  • Human approval before any side effect
  • Cancel anytime · full audit trail

Target UX Durable job proposals, opt-in host claims and fenced reports are already built in the prototype.

Tell this as a story. One sentence of direction fans out to four agents across support, operations, dev and PM. The guardrails are what make autonomy deployable: approval is bound to the exact action content, so an agent can't get approval for X and then do Y. Be clear this is the target flow; job lifecycle, claims and fencing exist today.
Pillar 3 · NVIAI = New Vision AI & IoT

Intelligence at the edge, frontier models on demand

  • Every site that runs the app runs its own data node. Nodes sync peer to peer with replicas instead of depending on one central server.
  • Edge AI on Macs and IoT gateways handles the everyday work: classification, extraction, summaries, vision on cameras and sensors.
  • IoT streams stay local. Only typed events enter the ledger.
  • LLM nodes run frontier models that local hardware can't. They're called only with minimal, permission-filtered context.
  • Lower server bills, data stays private, and work continues offline.
NVIAI stands for New Vision AI & IoT. Each location that runs Monastack is also a node: app + local model + data replica. A process node is always on for agents and the Codex runner; a media node handles WebRTC/LiveKit. Nodes replicate peer to peer, so there's no single expensive server. LLM nodes are the escape hatch for frontier-grade reasoning and coding that a laptop can't run.
Pillar 3 · Routing

Send every task to the right model

EDGE · LOCAL MODEL

Fast, private, offline

  • Classify & route tickets
  • Extract fields into schemas
  • Redact PII before escalation
  • Summarize meetings & threads
  • Camera / sensor events (IoT)
PROCESS NODE · ALWAYS ON

Runs the agents

  • 24/7 agent jobs & schedules
  • Codex runner in a sandbox
  • Workflows & approvals
  • Same Rust core as the app
  • Scoped service identity
LLM NODE · FRONTIER

Deep reasoning

  • Multi-step planning
  • Code generation & review
  • Long-form drafting
  • Hard analysis across departments
  • Only with minimal context packs

Routing signals: data sensitivity · difficulty · latency · cost · connectivity

Measured Qwen3-0.6B-4bit on an Apple M6 Mac: 0.32 s load · ~352 tok/s generation · 0.5 GB peak MLX memory (single synthetic run)

The economics: most company AI work is small and frequent (classification, extraction, summarization), and it belongs on the edge. Frontier models are reserved for hard reasoning and code. The measurement is real, from our local-model spike, and it's a single warm run, not a quality benchmark.

3 · VERIFY

Codex has to run, measure and report real results, and label anything fake

Capability matrix + ADRs keep each stage honest

Codex as the Dev Agent's engine

  • Process node claims an approved job (durable, fenced)
  • Runs codex exec in a networkless, read-only, non-root container
  • PID / memory / CPU limits, deadline, watchdog, cancel
  • Output becomes a PR for human review, never a silent merge
  • Agent identity stays separate from the coding engine, so engines can be swapped
Judging criterion: how effectively Codex was used. Two layers: (1) our development process is spec- and prompt-driven with Codex, with strict verification rules; (2) inside the product, Codex is the runtime for the Dev Agent, sandboxed and approval-gated.
